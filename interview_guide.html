1. The 2-Minute Elevator Pitch (How to start your interview)

The Problem: Internal IT and HR support teams are inundated with repetitive inquiries ("VPN drops", "expense limit", "battery dying"). Traditional portals require manual categorization, manual triage, and manual drafting, causing high resolution times.

What QuickDesk is: QuickDesk is an AI-assisted internal helpdesk platform where the LLM acts as an intelligent co-pilot rather than replacing the human agent.

  • Automatic Triage: The moment an employee files a ticket, the backend executes LLM classification to predict Category (IT, HR, Finance, Admin, Other), Priority (Low, Medium, High), and a confidence score.
  • Grounded RAG Draft: Using LangChain and FastEmbed vectors over internal markdown policies, it pre-drafts an actionable reply with citations so the agent never starts from a blank page.
  • Human in the Loop: The agent retains full authority. They can override categories/priorities (which logs to an immutable audit trail) and customize the draft before hitting Send.
  • Real-Time Updates: Socket.IO broadcasts updates without page reloads—new tickets pop onto agent dashboards live, and employee ticket badges flip to "Resolved" instantly.

3. Roles & Permissions: Employee vs. Agent

Employee Role

What Employees Can Do

  • Submit tickets (Title, description, attachment filename).
  • View ONLY their own tickets under "My Tickets".
  • Receive instant live updates when their ticket flips to "Resolved".
  • Inspect the final reply sent by the support team.

⛔ Backend Restriction: If an employee queries GET /api/tickets/99 belonging to another employee, FastAPI raises HTTP 403 Forbidden.

Support Agent Role

What Support Agents Can Do

  • View ALL company tickets across all employees.
  • Filter by Status, Category, Priority, and Search on Title.
  • Override AI suggestions (changes are logged in audit history).
  • Review RAG citations and edit the AI-drafted reply.
  • Click "Send Reply" to resolve the ticket.
  • Access the Operations Metrics Dashboard.

5. The AI Engine: Category Assignment, Confidence Score & Triage Guardrails

1. How Category is Assigned by the LLM (Architecture & Pipeline)

In backend/app/services/ai_service.py, ticket classification does not treat the LLM as a chatty assistant. Instead, it operates as a strictly constrained token classifier governed by a multi-stage ingestion and sanitization pipeline: 

[Raw Ticket Submission] (Title + Description)
       │
       ▼
[Stage 1: In-Context Prompt & Constraint Injection]
       ├── Sets Persona: "Internal IT Helpdesk triage classifier"
       ├── Enforces Discrete Enum Space: [IT, HR, Finance, Admin, Other]
       ├── Sets Temperature = 0.2 (low variance, argmax greedy sampling)
       └── Enforces Raw JSON Output Schema: {"category": "...", "priority": "...", "confidence": ...}
       │
       ▼
[Stage 2: Provider Invocation Layer]
       ├── Primary Online: Hugging Face (Llama-3.2-3B-Instruct) / Groq API (llama-3.1-8b-instant)
       └── Fallback Engine: Deterministic Rule-Based NLP if offline, unkeyed, or rate-limited (HTTP 429)
       │
       ▼
[Stage 3: Non-Greedy Regex JSON Extractor]
       └── re.search(r"\{.*?\}", raw_output, re.DOTALL)
       └── Strips Markdown code fences (```json ... ```) & conversational preamble ("Here is the triage:")
       │
       ▼
[Stage 4: Normalization & Exact Enum Validation]
       └── Case-folding & whitespace trimming against TicketCategory.ALL
       │
       ▼
[Stage 5: Fuzzy Synonym & Alias Mapping (CATEGORY_MAP)]
       ├── "vpn", "wireguard", "laptop", "wifi", "software" ──▶ Maps to "IT"
       ├── "pto", "vacation", "sick leave", "bamboohr"       ──▶ Maps to "HR"
       ├── "reimbursement", "expensify", "payroll", "budget"  ──▶ Maps to "Finance"
       └── "badge", "parking", "keycard", "desk", "office"   ──▶ Maps to "Admin"
       │
       ▼
[Stage 6: Fail-Safe Default Fallback]
       └── If unrecognized/hallucinated (e.g. "Legal"), safely defaults to "Other" (Never 500s!)

The Exact Prompt Template Used:

prompt = f"""You are an internal IT Helpdesk triage classifier.
Given the ticket title and description below, classify it into:
1. Category: Exactly one of [IT, HR, Finance, Admin, Other]
2. Priority: Exactly one of [Low, Medium, High]
3. Confidence: A decimal between 0.0 and 1.0

Ticket Title: {title}
Ticket Description: {description}

Respond ONLY in valid JSON format:
{{"category": "IT", "priority": "High", "confidence": 0.95}}"""
Why Low Temperature (0.2)? For creative prose or chatbots, high temperatures (0.7–1.0) produce varied responses. In enterprise triage, variability is a defect. A temperature of 0.2 concentrates the probability distribution around the argmax tokens, maximizing deterministic consistency.

2. The AI Confidence Score: Mathematical Logic, Calculation & Purpose

Every classified ticket receives an ai_confidence_score stored in PostgreSQL and rendered as a visual badge in the agent portal (e.g., 94% AI Confidence).

How the Confidence Score is Calculated:

  • Online LLM Generation (Model Self-Assessment): The prompt forces the model to evaluate the linguistic ambiguity and semantic alignment between the ticket details and the target category.
    • High Confidence (0.90 – 0.98): Unambiguous symptoms matching known technical jargon (e.g., "WireGuard UDP 51820 TLS handshake timeout").
    • Moderate Confidence (0.75 – 0.88): Standard requests with slight cross-domain overlap (e.g., "Need access to the budget planning drive" — IT drive permission vs. Finance ownership).
    • Low Confidence (< 0.75): Short, ambiguous, or multi-topic descriptions (e.g., "I need help with my work environment").
  • Sanitization & Boundary Clamping: Real models might return numbers like 1.5 or strings like "high". The backend enforces mathematical bounding: 
    confidence = float(data.get("confidence", 0.85))
confidence = max(0.1, min(1.0, confidence))  # Clamped strictly to [0.10, 1.00]
return round(confidence, 2)
  • Offline Deterministic Heuristic Scoring: When operating in offline/mock mode, confidence is computed using keyword match density and token specificity:
    Classification Match Type Sample Trigger Keywords Assigned Confidence Score
    Primary IT Core Signals vpn, wireguard, wifi, macbook, thinkpad 0.94 (94%)
    Primary HR Core Signals pto, vacation, sick leave, bamboohr 0.91 (91%)
    Primary Finance Core Signals expensify, reimbursement, invoice, payroll 0.89 (89%)
    Primary Admin Facilities Signals badge, keycard, desk, parking 0.85 (85%)
    Generic / Unclassified ("Other") No domain keywords found (fallback) 0.70 (70%)

Why Confidence Scores Matter in Enterprise Architecture (Interview Talking Points):

1. Human-in-the-Loop Triage Filter

Agents can glance at the badge to see if the AI's triage was high-certainty or borderline. Borderline tickets receive extra scrutiny before routing or replying.

2. Automated Routing Thresholds

At scale, tickets with ≥ 95% confidence can be auto-routed to Tier-1 resolvers without human triage delay, while tickets with < 80% confidence trigger mandatory human review.

3. Model Drift & Calibration Auditing

By comparing initial confidence against agent overrides (logged in ticket_override_logs), engineering teams calculate model calibration error to detect prompt degradation over time.

4. Fallback Safety Net

Guarantees that low-confidence tickets default to a safe Other category and Medium priority without throwing database validation exceptions.

6. The LangChain RAG Pipeline & In-Memory Vector Store

Located in backend/app/services/rag_service.py. Here is exactly how it is structured:

1. Knowledge Base Articles (7 Markdown files)

Stored in backend/app/kb/ (150–250 words each): vpn_setup.md, password_reset_policy.md, leave_application_process.md, expense_reimbursement.md, laptop_request.md, finance_drive_access.md, and software_license_request.md.

2. Chunking

Uses RecursiveCharacterTextSplitter(chunk_size=400, chunk_overlap=50). 400 characters captures self-contained policy paragraphs, and 50 characters overlap prevents losing context at chunk boundaries.

3. Embeddings: Why FastEmbed?

Standard PyTorch sentence-transformers downloads a 550MB PyTorch wheel and 1.5GB of CUDA drivers. Instead, we use FastEmbed (BAAI/bge-small-en-v1.5):

  • Runs on pure ONNX runtime.
  • Requires ~60MB RAM footprint.
  • Executes 4x faster on CPU with zero GPU dependencies.

4. Similarity Threshold Calibration & Anti-Hallucination Guardrail

Chunks are indexed in an in-memory FAISS vector store. In FAISS L2/Euclidean distance, lower numbers mean higher relevance.

Query Type Sample Query Measured Distance Score Outcome
Relevant "WireGuard VPN disconnects timeout" 0.5049 Match (Accepted)
Relevant "How do I claim reimbursement in Expensify" 0.5327 Match (Accepted)
Relevant "Laptop battery drains quickly ThinkPad" 0.7297 Match (Accepted)
Irrelevant "What is the recipe for cookies on Mars?" 1.0715 Rejected (Guardrail Triggered)
The Guardrail Rule: If the distance score is > 0.88, the system triggers the guardrail: is_relevant = False and citations = [].
The AI generates an honest fallback reply: "I could not find relevant documentation in our internal knowledge base for this request. I have forwarded this ticket to our support team." (Zero hallucinations!).

7. Faceted Searching & Multi-Dimensional Query Engine

Located in backend/app/api/tickets.py and frontend/src/pages/AgentDashboard.jsx.

1. What is Faceted Searching vs. Simple Search?

Traditional search is a single free-text input (e.g. typing a keyword into a bar). Faceted Search allows support agents to simultaneously filter a dataset across multiple independent, orthogonal dimensions (facets) to isolate high-urgency subsets of work:

Facet Dimension Allowable Values in QuickDesk Operational Purpose for Support Team
Status Facet All, Open, Resolved Isolate active work queue vs. historical closed records.
Category Facet All, IT, HR, Finance, Admin, Other Route to specialized departmental squads (e.g. IT engineers only review IT tickets).
Priority Facet All, Low, Medium, High SLA triage (e.g. "Show me all Open High-Priority tickets that need immediate response").
Full-Text Query Free-text string (e.g. "WireGuard", "Expensify") Substring keyword search across ticket titles and descriptions.

2. Backend Dynamic Query Compilation in SQLAlchemy

Instead of writing separate SQL queries for every permutation of filters, the backend dynamically composes the query using SQLAlchemy's declarative builder pattern: 

@router.get("", response_model=List[TicketResponse])
def list_tickets(
    status_filter: Optional[str] = Query(None, alias="status"),
    category_filter: Optional[str] = Query(None, alias="category"),
    priority_filter: Optional[str] = Query(None, alias="priority"),
    search: Optional[str] = Query(None),
    current_user: User = Depends(get_current_user),
    db: Session = Depends(get_db)
):
    query = db.query(Ticket)

    # 1. Mandatory Role-Based Access Control Scoping
    if current_user.role == UserRole.EMPLOYEE:
        query = query.filter(Ticket.created_by_id == current_user.id)

    # 2. Dynamic Facet Evaluation (Conjunctive AND Logic)
    if status_filter and status_filter.lower() != "all":
        query = query.filter(Ticket.status == status_filter.lower().strip())

    if category_filter and category_filter.lower() != "all":
        query = query.filter(Ticket.category == category_filter.strip())

    if priority_filter and priority_filter.lower() != "all":
        query = query.filter(Ticket.priority == priority_filter.strip())

    # 3. Case-Insensitive Full-Text Search across Title OR Description
    if search and search.strip():
        search_pattern = f"%{search.strip()}%"
        query = query.filter(
            or_(
                Ticket.title.ilike(search_pattern),
                Ticket.description.ilike(search_pattern)
            )
        )

    # 4. Strict Chronological Ordering
    return query.order_by(Ticket.created_at.desc()).all()

The Compiled SQL Produced by PostgreSQL:

SELECT tickets.id, tickets.title, tickets.status, tickets.category, tickets.priority, ...
FROM tickets
WHERE tickets.status = 'open'
  AND tickets.category = 'IT'
  AND tickets.priority = 'High'
  AND (tickets.title ILIKE '%vpn%' OR tickets.description ILIKE '%vpn%')
ORDER BY tickets.created_at DESC;

3. Frontend UX & Reactive State Management

In frontend/src/pages/AgentDashboard.jsx, faceted search is made responsive and resilient through key engineering patterns:

  • Reactive Multi-Select Synchronization: Changing any dropdown (Status, Category, Priority) triggers an immediate re-fetch via useEffect([statusFilter, categoryFilter, priorityFilter]).
  • 300ms Debounced Free-Text Search: 
    // Debounced search: waits 300ms after user pauses typing before firing HTTP query
useEffect(() => {
  const timer = setTimeout(() => {
    fetchTickets();
  }, 300);
  return () => clearTimeout(timer);
}, [search]);
    Why Debouncing is Critical: If an agent types "WireGuard" (9 characters), an un-debounced input would trigger 9 rapid HTTP requests to the backend. This wastes database IOPS, clutters network bandwidth, and causes race conditions where request #4 might resolve after request #9, displaying stale results. The 300ms timer buffers keystrokes and fires only 1 optimized query.
  • WebSocket State Blending: When an employee files a new ticket, the incoming ticket_created Socket.IO event prepends the ticket into the React state array without triggering a full-page reload or resetting the agent's active filter selections.

8. Real-Time WebSockets: Socket.IO Architecture

Located in backend/app/services/socket_service.py.

How Rooms Prevent Data Leakage

When a client connects to Socket.IO, it passes its JWT token in the auth handshake: 

def get_user_rooms_for_token(token: str) -> List[str]:
    payload = decode_access_token(token)
    role = payload.get("role")
    user_id = payload.get("sub")

    rooms = []
    if role == "agent":
        rooms.append("agents")          # Global broadcast channel for agents
    if user_id:
        rooms.append(f"user_{user_id}") # Private room for specific employee

    return rooms
Security Benefit: Employees never join the agents room. When new tickets are filed, the broadcast is scoped strictly to room agents. Employees cannot sniff network packets to see tickets filed by other coworkers.

2. tickets Table

  • id: Integer Primary Key (Autoincrement)
  • title: String(255)
  • description: Text
  • attachment_filename: String(255) Nullable
  • status: String(20) — 'open' or 'resolved'
  • category: String(50) — Effective category (IT, HR, Finance, Admin, Other)
  • priority: String(20) — Effective priority (Low, Medium, High)
  • ai_suggested_category: String(50) — Immutable record of initial AI prediction
  • ai_suggested_priority: String(20) — Immutable record of initial AI prediction
  • ai_confidence_score: Float Nullable
  • ai_drafted_reply: Text — Original RAG draft preserved for comparison
  • final_reply: Text — The actual reply sent by the agent
  • citations: JSON — Array of cited article titles and snippets
  • created_by_id: Foreign Key $\to$ users.id
  • resolved_by_id: Foreign Key $\to$ users.id Nullable
  • resolved_at: DateTime(UTC) Nullable

3. ticket_override_logs Table

  • id: Integer Primary Key
  • ticket_id: Foreign Key $\to$ tickets.id
  • agent_id: Foreign Key $\to$ users.id
  • field_name: String(50) — 'category' or 'priority'
  • from_value: String(50) — Previous value
  • to_value: String(50) — New overridden value
  • created_at: DateTime(UTC)

11. Tough Technical Interview Questions (The "Grill Me" Section)

Q1: "Why not use Next.js instead of separate React + FastAPI?"

Your Answer: "Next.js is primarily built for Server-Side Rendering (SSR) and public web apps where SEO matters. QuickDesk is an internal enterprise tool behind an authentication wall where SSR provides zero SEO benefit. Separating React and FastAPI gives us a clean separation of concerns: our Python backend can run high-performance asynchronous AI/ML workloads and WebSockets on ASGI, while the frontend is a lightweight Single Page Application that can be compiled to static assets and served behind Nginx."

Q2: "Where did you store the JWT on the client, and what is the security tradeoff?"

Your Answer: "We stored the JWT in localStorage. The tradeoff is that localStorage is vulnerable to Cross-Site Scripting (XSS) if untrusted third-party scripts execute. Using HttpOnly cookies prevents XSS reading, but introduces Cross-Site Request Forgery (CSRF) vulnerabilities and complicates WebSocket handshake authentication. For this internal enterprise SPA where no untrusted third-party JavaScript runs, localStorage provided the cleanest transport for both REST Authorization headers and Socket.IO connection handshakes."

Q3: "What stops an employee from hitting an agent-only endpoint by guessing the URL?"

Your Answer: "Role enforcement is not handled in the frontend UI—it is strictly enforced at the FastAPI dependency layer. Every agent endpoint declares current_user: User = Depends(require_agent). When a request arrives, the dependency extracts the JWT, verifies the signature, and checks the user's role in the database. If an employee hits the URL, FastAPI halts execution immediately and raises an HTTP 403 Forbidden before any business logic or database query can run."

Q4: "What is the worst failure mode in your system today, and how would you fix it?"

Your Answer: "Today, the FAISS vector index is in-memory. If the backend process crashes or restarts, it re-indexes the markdown documents from disk at startup. While this takes under 1 second for 7 documents, in an enterprise with 50,000 policy documents, rebuilding an in-memory index on every restart would cause heavy startup latency. The production fix is to migrate from in-memory FAISS to pgvector directly inside our PostgreSQL database. This allows atomic migrations, persistent vectors alongside ticket data, and hybrid keyword + vector search."

Q5: "Why Socket.IO over Server-Sent Events (SSE) or native WebSockets?"

Your Answer: "While SSE is lightweight for one-way streams, Socket.IO provides bi-directional communication, built-in room management (allowing us to separate the agents broadcast channel from individual user_{id} channels), automatic heartbeat monitoring, and automatic fallback from WebSockets to HTTP long-polling if corporate firewalls block raw WebSocket upgrades."

Q6: "Why did you disallow modifying priority and category on already resolved tickets?"

Your Answer: "In ticket lifecycle design, once a ticket reaches a terminal state (Resolved/Closed), operational attributes like Priority and Category must become immutable. In QuickDesk, we enforce this at both the FastAPI API layer (returning 400 Bad Request) and the React UI layer (locking the controls). There are two core architectural reasons for this: First, Metrics & SLA Integrity: Priority governs queue triage urgency and SLA targets while work is active. If an agent changes priority retrospectively, it corrupts historical SLA compliance reports and MTTR (Mean Time to Resolution) analytics in /api/metrics. Second, Auditability & Dispute Prevention: Modifying attributes after resolution compromises audit credibility. In enterprise architectures (like ServiceNow or Jira Service Management), if a ticket was genuinely misclassified, the business rule requires an explicit Reopen workflow first, rather than silently mutating closed records."
